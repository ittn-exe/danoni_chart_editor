# 進捗・残りTBD・将来実装可能性まとめ(2026-07-22時点)

β版公開の判断材料として、実装済み機能の全体像・現時点で残っているTBD・「将来実装するかもしれないが今は着手しない」項目を整理する。
最後に、公開形態(単独EXEで配布できるか)についての確認結果も記載する。

## 1. 実装済み機能(全体)

### コア設計

- tickベースのタイミング管理(`TimingEngine`)、tick↔frame変換、拍子/BPM変化点対応
- テンプレート形式(`./template/temp_{keyTypeId}.json`、`KeyTemplate`/`LaneDef`)。24キー種分を収録
- プロジェクトファイル形式(JSON、`ProjectSerializer`、schemaVersion移行対応)
- Undo/Redo(`IEditAction`/`CompositeEditAction`/`UndoStack`、保持件数を環境設定で変更可)
- FUJIエディタ形式・SKBエディタ形式・dos.txt単体のインポート/エクスポート
- D&Dによるファイル読み込み(自形式/FUJI/SKB/dos.txt/BASE64楽曲データ/生音源ファイルを中身から判定)

### 譜面編集エリア

- マウスモード(スマートツール/個別ツール)・SKB操作モード(キーボード入力)の両対応
- キーボードモードの小節移動・現在位置ライン自動スクロール(譜面ビューのReverse設定に追随)
- ncolor_data個別色編集モード(通常色/ヒット時色/塗りつぶし色、一括塗り、履歴)
- コメント・警告(Annotations)。インポート時の丸め処理等を自動記録し、警告アイコンを譜面ビューに重ね描き
- 範囲選択・クリップボード(プロジェクトを跨いだ貼り付け)・全選択(Ctrl+A/Shift+Ctrl+A対象種別を環境設定で選択可)
- フレーム情報モード(拍情報モードとの相互変換)
- レーン入替マクロ(仕様書11章): `MacroEditorWindow`で順列を定義し、右パネルから実行(Undo対応)。対象キー種を変更する際は入れ替え内容が失われる旨の確認ダイアログを表示(事故防止、2026-07-31)

### プレイテスト・目視テスト

- プレイテスト画面(判定・コンボ表示、オートプレイ、ハイスピード/オフセット/ウィンドウ倍率、中断キー選択、speed_data/boost_data反映)
- 目視テスト(再生位置ラインの追従方式選択: ページ送り/スムーズスクロール)
- 再生速度・音量の共通設定(スライダー+数値入力欄、プレイテストにも反映)

### 右パネル/環境設定/その他UI

- プロジェクトプロパティ・色設定・選択中オブジェクト・その他ヘッダー(カテゴリ別折りたたみ)の4タブ構成
- 右パネルの自動切り替えは「単体オブジェクトをクリックした時のみ」に限定(複数選択時は切り替えない、2026-07-31要望対応)
- 環境設定ウィンドウ(カテゴリ式、表示/目視テスト/プレイテスト/新規プロジェクト/編集保存/キーボードモード/musicURL取得/テンプレート)
- `TemplateEditorWindow`(テンプレート新規作成・編集): レーンごとのタブ編集・D&D並び替え・プレビュー帯・`fujiLaneNum`入力欄(レーン入れ替えに追随、空欄可=`displayOrder`を代用、2026-07-31)
- musicURLからの楽曲自動取得機能、最近開いたファイル、起動スプラッシュウィンドウ

### ゲージ設定(customGauge/gaugeXXX、2026-08-01新規)

- `GaugeEditorWindow`(設定メニューから起動)
  - ①難易度タブごとのゲージ名リスト編集(「指定しない」「継承キーワード(survival/border/customDefault)」「明示リスト(name::F|V::表示名)」の3択、難易度ごとに異なるリストを完全サポート)
  - ②ゲージ別パラメータ(ノルマ/回復/ダメージ/初期ライフ)をプロジェクト全体で共有するテーブル形式で編集
  - ③直接入力モード: プロジェクト全体で1つのテキスト欄。dos.txtのゲージ関連ヘッダー行をそのまま貼り付けられ、内容がある間は①②より常に優先される(過去資産からのコピペ用途)
- 実装前にdanoniplus本体ソース(`danoni_main.js`/`danoni_constants.js`)の`resetCustomGauge`/`getGaugeSetting`/`setGauge`を確認し、Wikiベースの理解が正しいことを検証済み

### FUJIエディタ形式インポートの精度向上(2026-08-01)

ユーザー提供の実サンプル(`test23key_v2_dos (2).txt`)との突き合わせで、以下3件のバグを発見・修正:

1. フリーズ終点の位置は「絶対位置」ではなく「開始位置からの加算(additive)」だった
2. フリーズ終点の3桁プレフィックスは常に10進数(仕様書「Dは10進数値」通り)で、16進として解釈していたのは誤りだった
3. `T`/`X`は16分グリッドとの整合(pp%32)に関わらず常に±8固定だった(以前は整合時のみ±8と暫定していたが誤り)

詳細・検証過程は`docs/fuji_format_notes.md`を参照。

### 2-5. 歌詞表示機能(word_data)未対応(2026-08-02追加)

仕様: [dos-e0003-wordData](https://github.com/cwtickle/danoniplus/wiki/dos-e0003-wordData)。ステップゾーン上下に表示する歌詞テキストを、フレーム位置ごとに設定する機能(`word_data`)。

- 1エントリ = `Frame, Position(偶数=上段/奇数=下段), Lyrics` の3項目。改行区切り。
- 制御用エントリとして `[fadein]` `[fadeout]` `[left]` `[center]` `[right]` `[fontSize=XX]` のキーワード行(3項目目がキーワード、4項目目にfadeFrame任意)や、`-`(コメント専用行)もある。
- データ名は用途別に多数存在(`word_data`/`word2_data`/`wordRev_data`(リバース専用)/`wordAlt_data`・`wordCross_data`等(Scroll拡張用)/`wordJa_data`・`wordEn_data`(言語別)/`wordA*_data`(別キーモード用)、かつ他譜面データの流用記法もある)。優先順位ルールも存在する(通常/リバース×言語指定有無×譜面番号で最大8段階)。

エディタ側の対応方針(ユーザー要望、2026-08-02): 任意に利用可能な「歌詞入力レーン」を設け、既定OFF・上部パネルのトグルボタンで表示/非表示を切り替えられるようにする。レーン上にオブジェクトとして歌詞を配置・編集できる形を想定。データ名のバリエーション(言語別/Scroll別/別キーモード別)まで全対応するか、まずは基本の`word_data`/`wordRev_data`のみ先行対応するかは実装時に要検討。

### 2-6. カレント難易度タブのみをdosエクスポート(合作用、2026-08-02追加)

複数人で1曲を分担制作する「合作」用途で、プロジェクト全体ではなく現在開いている難易度タブ1つ分だけをdos.txtとして書き出す機能。単体タブ出力時はサフィックス番号を持たない(先頭タブ相当の無サフィックス形式に振り直す)想定。

ユーザーからの検討事項: エクスポート時に何を含めるか(サフィックス採番のやり方、その他ヘッダー・共通設定をどこまで含めるか等)をチェックボックスで選べるようにすべきか、という論点が未確定。実装時に具体的な選択項目を洗い出して決める必要がある。

### 2-7. その他

## 3. 将来実装の可能性(TBDとは別枠、2026-07-31ユーザー確定の分類)

以下は「今は実装しないが、需要があれば将来実装する可能性がある」項目。TBD(未解決の実装課題)とは異なり、現時点で着手予定が無いことが確定している事項。

1. **FUJIエディタへのエクスポート機能**: 現段階では実装予定なし。当エディタはFUJI/SKB形式に対して現状「インポートのみ」対応。
2. **SKBエディタへのエクスポート機能**: 同上、現段階では実装予定なし。
3. **ラベル密集時の省略表示**: speed/boost/BPM等のイベントタグが密集した際、「メモリ(パフォーマンス)が厳しくなった時にだけ省略する」という方向性の実装可能性はあるが、監視コストに見合う需要が今のところ無く、必須機能とはしない。
4. **テンプレートエディタによる(CW Edition本体で使う)"カスタムキーテンプレート作成"機能**(2026-08-01追加): 当エディタの`TemplateEditorWindow`で作成したテンプレートを、danoniplus本体(CW Edition)側の「カスタムキーテンプレート」としてもそのまま使える形で書き出す機能。「エディタでテンプレを作ったのに本体用のテンプレをもう1回作るのが面倒」という動機で、理想としては「オリジナルキー種の編集から本体適用までを当エディタだけで一括して行える」状態を目指すもの。現時点では必要性が低いため着手せず、将来実装の可能性としてのみ記録する。

## 4. 配布形態についての確認結果

`dotnet publish -r win-x64 -p:PublishSingleFile=true --self-contained true` で実際にpublishし、出力フォルダの中身を確認した。結果、**単独EXEファイルのみでの配布は不可能**で、以下のファイルがexeと同じフォルダに残る:

- `D3DCompiler_47_cor3.dll`
- `PenImc_cor3.dll`
- `PresentationNative_cor3.dll`
- `vcruntime140_cor3.dll`
- `wpfgfx_cor3.dll`

これはWPF(Windows Desktop)アプリ全般に共通する.NET SDK側の既知の制約で、self-contained + single-file publishを行っても、上記のネイティブ相互運用DLL群だけは単一exeに埋め込めず、必ず別ファイルとして出力される仕様(当エディタ固有の問題ではない)。

加えて、`template`フォルダ(24キー種分のテンプレートJSON)は`.csproj`の設定により常にexeと同じ階層へコピーされる。`img`フォルダはリポジトリに存在しない場合はコピーされない(`Condition="Exists('..\..\img')"`)ため、想定通り「imgフォルダの中身はエディタ利用者が用意する」前提のままで問題ない。

まとめると、公開時のZIP等には最低限「exe本体+上記5個の付随DLL+templateフォルダ」を含める必要があり、「EXEファイル単体」での配布はできない。

> **2026-09-20追記**: 上記5個の付随DLLは、以後publish後に自動で`lib`サブフォルダへ移動されるようになった
> (exe本体ディレクトリを直下だけスッキリさせたいというユーザー要望対応)。詳細は
> `docs/realtime_collab_edit_design_2026-09-20.md`の「配布ディレクトリ整理」の項を参照。
> 「exe本体+lib フォルダ(付随DLL5個)+templateフォルダ」を含める必要がある点は変わらない。

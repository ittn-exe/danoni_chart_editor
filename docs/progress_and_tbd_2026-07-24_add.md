## 1. アーキテクチャ方針の更新(旧§4を上書き)

`ittn_analyzer_integration_handoff.md` §4では「選択肢B: DosExporter + Jint」を推奨としていたが、
本セッションで**「選択肢A: 本体(C#)への移植」を正式方針として採用**する。

### 1-1. 方針転換の理由

- JS版アナライザー(`analyzer_and_viewer/analyze.js`)は、界隈的には「誰も本格的に使っていない
  話題作りのおもちゃ」程度の位置づけであり、ロジックの正本をエディタのC#版に一本化しても
  実害がない、とのユーザー判断。
- 今後のロジックアップデートはエディタ(C#版)を基準に行い、JS版へは「思い出した頃に」
  フィードバックする片方向運用でよい(=旧方針が懸念していた「係数変更のたびに両方直す」
  という双方向の二重メンテ問題は、そもそも双方向を維持する必要がないため消滅する)。

### 1-2. 移植の進め方(2段階)

1. **忠実移植パート**: `analyze.js`のロジックをそのままC#へ書き写す(`DifficultyLevelCalculator.cs`
   と同様の前例踏襲スタイル)。この段階ではBPM強化を行わず、JS版との数値一致を確認する。
   - 検証用リファレンス実装として `danoni_chart_collector/collector-app/AnalyzeEngine.cs`
     (Jint経由でanalyze.js本体を無改造実行するブリッジ、Node.js版との数値一致を検証済み)が
     使える。**このファイルは`analyzer_and_viewer`ではなく`danoni_chart_collector`配下に
     あることが判明した(旧ドキュメントの参照パス記載は誤り、要修正)**。
   - `analysis_log.csv`(約1700件の実測データ)を突き合わせテストの材料として使う想定。
2. **BPM強化パート**: 1で忠実移植が確認できたのち、tick/BPM情報を使った機能強化を
   別段階として加える(詳細は§2)。

## 2. 「BPM情報を使ったグレードアップ」の具体化

エディタが従来のJS版アナライザーと異なり「tick単位の正確なBPM/拍情報」を保持している点を
活かす強化。ただし**取得すべき評価要素自体はJS版の段階で既に出揃っており、今回強化するのは
主に「frame数決め打ちだったスライディング窓を、BPM/小節基準に置き換える」精度改善**である
(裏拍検出のような新規要素の追加は、今回はスコープ外。将来「やった方が良い」となれば検討)。

frame決め打ちの窓のうち、置き換え候補として洗い出し済みのもの:

| 対象 | 現行(JS版) | 備考 |
|------|-----------|------|
| VOLTAGE | 4秒スライディング窓 | ユーザー指摘の代表例。小節情報で置き換え候補の筆頭 |
| ALT | `PEAK_WINDOW`=600F(10秒固定、局所難所検出) | |
| MOV | `PEAK_WINDOW`=600F、`SIMUL_WINDOW`=15F(出張候補探索) | |
| DISCARD | `WINDOW`=120F(2秒、捨てノーツ判定) | |
| SOFLAN | `TIME_WINDOW_B`=120F(変速直後の読み直し負荷判定) | |

各関数ごとに「何小節/何拍基準に置き換えるか」は、移植作業を進めながら個別に判断する
(本セッションでは方向性の確認のみ、詳細設計は着手時)。

## 3. 推定star値のキャリブレーション方針

### 3-1. サンプルカバレッジについて

難易度表由来のサンプル(n≈1700、`ittn_analyzer_integration_handoff.md`§6参照)は、
CW Edition全24キー種のうち以下9区分のみをカバーしている(難易度表というものの性質上、
全キー種を網羅していない):

片手5Key / 両手5Key / 7key / 7ikey / 11key / 11Lkey / 12key / 9Akey / 9Bkey

(9A/9Bは★行が存在せず、実データ上は常に☆側の値のみを取る特殊仕様。詳細は
`ittn_analyzer_integration_handoff.md`§7参照)

残り約15キー種のサンプルを得るには「譜面データベース」(2サイト)向けの専用dos取得ソフトを
別途作る必要があるが、**既存9区分の回帰の当てはまり(相関係数換算で最低の5keyでも約7割、
最高の9A/9Bで約9割)を踏まえ、追加の取得ソフト開発は行わない方針で確定**した。
今後キー種を追加したくなった場合のTBDとしてのみ記録しておく(§5参照)。

### 3-2. 回帰方式

キー種ごとの個別回帰(`ittn_analyzer_integration_handoff.md`§6の表形式)ではなく、
**全キー種を統合した単一の回帰(統合回帰)**を採用する方針。具体的な回帰式の形
(キー種を無視した単純回帰か、キー種を説明変数に含めた重回帰か)は、実際に手持ちの
再フィット用資料を使って再検証する段階(実装着手時)で決定する。

### 3-3. 確率幅の算出方式

「☆1:0%、☆2:2%…」のような内部確率算出→60%を超える幅を表示、というアイデアについては、
**残差分布(正規分布を仮定)から信頼区間を求める方式(旧提示の(a)案)を採用**することで確定。
個々のstar値ラベルごとの単体確率が60%を超えるかを見る方式((b)案)は不採用。

### 3-4. 表記

- **整数表記のみ**とする(実在の難易度表自体が整数表記のため、それに合わせる)。
- 「☆/★」のような実在表記に似せた見せ方はしない。**「おにスター: 10〜15個」のような、
  実在の難易度ラベルと混同しない、あえて曖昧にした独自名称で表示する**仮方針
  (正式名称は着手時に改めて検討)。「STAR: 10〜15」等の中間案も検討したが、最終的に
  「おにスター」寄りの、実在表記から意図的に距離を置く方向で合意。

## 4. 隠し機能としての実装方針

ITTNアナライザー(難易度分析)・推定star値の両機能は、**隠し機能(イースターエッグ的な扱い、
実績解除または隠しコマンドでの解禁を想定)として実装する**方針。

- 解禁条件の具体案は現時点では未定・後回しでよい。
- 実装順序は「ロジック(Analysis層)を先行して完成させ、UIへの配線(ボタン設置・解禁条件との
  接続)は解禁条件が固まった段階で行う」。
- この方針により、Analysis層(`IttnAnalyzer`仮称)はUIから独立して単体で動作・テスト可能な
  設計にしておく必要がある(元々`ittn_analyzer_integration_handoff.md`§5のステップ3で
  想定していた設計と整合)。

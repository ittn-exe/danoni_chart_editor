# プラグイン対応の設計方針(2026-07-26、雑談ベースの構想まとめ)

エディタに感銘を受けたユーザーが独自機能を作りたいとの声を受け、プラグイン形式による機能拡張の可否・設計方針を検討した際の議論の記録。まだ実装着手前の構想段階の内容だが、以後の実装の指針としてここに残す。

## 1. 発想の元ネタ

danoniplus本体の「カスタムJS」の思想に近い。エンジン本体を書き換えられるわけではなく、決まったタイミングで決まったAPIを呼べる程度の限定的な差し込み口を用意し、その範囲内で外部コードに機能を追加させる方式を目指す。

## 2. 現状のアーキテクチャへの影響

既存の3層構成(`DanoniEditor.Core` / `DanoniEditor.Editing` / `DanoniEditor.App`)は土台として維持する。プラグイン対応は既存コードの書き換えではなく、既存コードの隣に新しい層(拡張点)を足す加算的な作業と位置付ける。

局所的に手を入れる必要があるのは以下の2箇所のみ:
- `ChartCanvas`の描画処理: 本体の描画が完了した後にプラグインへも描画させる「オーバーレイ描画フック」を追加
- プレイテスト(`PlaytestWindow`)の再生ループ: 同様に、再生中の現在フレーム等をプラグインへ渡すフックを追加

それ以外の既存機能(譜面データモデル、Undo/Redo、インポート/エクスポート、既存UI画面)は変更不要。

## 3. 拡張レベルの3段階

### 段階1: 読み取り専用(可視化・解析系) — 最も軽量

譜面データを読み取り、パネル表示やオーバーレイ描画で完結するプラグイン。書き込み(譜面の変更)が発生しないため、公開すべきAPIが狭く、プラグイン側が本体を壊すリスクも低い。

例:
- 「11keyにおける右手移動の可視化」(相談のきっかけとなった具体例。右パネルへドッキングする設定パネル+譜面ビュー/プレイテスト画面へのオーバーレイ表示+レーン衝突検知)
- ノート密度のヒートマップ
- 独自の統計パネル
- リズムパターンの解析結果表示

### 段階2: 書き込み(編集)系 — 今回準備の対象

譜面データを実際に書き換えるプラグイン。Undo/Redoの仕組み(`IEditAction`)を安全に呼び出せる公開APIが必要になるため、段階1より設計は重くなるが、既存のUndo基盤に乗せる形なので実現は可能。

例:
- パターン自動配置プラグイン
- 独自ファイル形式のインポート/エクスポート追加プラグイン

### 段階3: エンジン中核の差し替え — 現時点では対象外

判定ロジック・ゲージ計算式の差し替え、マウス操作の基本挙動の変更、ノート自体の描画方法の変更など。オーバーレイ描画・読み取りAPIの提供程度では届かず、コア機能そのものにプラガブルな差し替え口を作り込む必要があり、大改造になる。**今回は対象外とする。**

## 4. 段階2までの土台として準備するもの

1. **外部DLLローダー**: `AssemblyLoadContext`ベースでプラグインDLLを安全に読み込む。プラグイン一覧の検出・有効/無効切替も含む。
2. **プラグインが実装する最小限のインターフェース群**: まずは以下2種類から。
   - UIパネルを右パネルへ差し込むインターフェース(設定画面込み)
   - 譜面ビュー/プレイテスト画面へのオーバーレイ描画を差し込むインターフェース
3. **Core層の読み取り専用公開API**: 譜面・レーン・タイミング情報などの内部モデルをそのまま渡すのではなく、安定した窓口(プラグイン向けAPI層)を経由して渡す。内部実装が変わってもプラグインが壊れないようにするための緩衝材。
4. **Undo/Redo経由の限定的な編集API**: いきなり全操作を解放せず、最初は「ノート配置/削除」程度の小さな範囲から始める。
5. **プロジェクトファイル側の「プラグイン用自由記述領域」**: プラグインが独自設定(例: 「どのレーンが右手か」)をプロジェクトファイルに保存できるよう、プロジェクト形式に自由記述領域を1つ予約しておく。後からの手戻りを減らす狙いで、段階1の実装より前に用意しておくのが望ましい。

## 5. 今後の運用方針

上記1〜5の土台さえ整えば、以後は個別のプラグインの要望が来るたびに「今のAPIで足りるか、足りなければどのAPIを足すか」を都度判断していく運用に移行する。最初から全ての用途を見越して設計し尽くす必要はない。

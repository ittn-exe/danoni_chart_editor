# FUJIエディタ形式 調査メモ(2026-07-25作成、2026-07-31更新)

`1224frztest.txt`(FUJIエディタネイティブ形式)と `1224frztest_dos.txt`(同ファイルをdanoniplus
dos.txtへエクスポートしたもの)をユーザーから提供頂き、全数比較でフリーズ関連の未確定事項を
解消した(2026-07-25)。同日、FUJI氏本人が執筆したとみられる公式サイト掲載のフォーマット
仕様書をユーザーから提供頂き、実データ検証だけでは区別しきれなかった項目の一部を公式情報で
確定できた。さらに同日、T/X/W fine文字と非ゼロ開始位置のフリーズ終点を意図的に含む
`test23key_v2.txt`/`test23key_v2_dos.txt`(23key)をユーザーから提供頂き、これらとの突き合わせで
**3件の実装バグ**を発見・修正した。本メモはその調査結果と、まだ確定しきれていない事項の記録。
実装は`src/DanoniEditor.Core/Import/FujiImporter.cs`に反映済み(該当箇所のXML docコメントにも
要約を記載)。

検証に使った1224frztestサンプルの前提条件: `$frame=0/2000/402000/1,400`(単一BPM区間、
mlen=100フレーム/小節、BPM=144、StartNumber(tick0フレーム)=200)。全5レーンが同じ
フリーズを同時に踏む譜面のため、`frzLeft_data`等5系統の出力はすべて同一の数値列になる。

test23key_v2.txtの前提条件: `$frame=0/2000/251350/1,400`(blank=200, 総フレーム=25135,
400小節、mlen=(25135−200)/400=62.3375)。23keyテンプレート使用。measure0〜10に
R/S/T/W/Xすべてのfine文字と、非拡張・拡張(`'9'`フラグ)両方のフリーズ終点、非ゼロ開始位置の
フリーズ終点を含む。**この検証で、note23点・freeze24ペアすべてが実測値と厳密一致することを
確認済み。**

## 2026-07-31(前半): 公式フォーマット文書との突き合わせ結果

ユーザー提供の公式文書(通常ノート`[ABBC]`、フリーズ`[ABBC-DDDE]`の構造を説明したもの)を
現行実装と突き合わせ、以下を確認した。

- **レーン/位置のビット構造は現行実装と数学的に完全一致(バグなし)。** 公式文書のB欄
  (`bit7=フリーズ、bit6=速度、bit[5:0]=レーン`)という説明と、現行実装の
  `ppRaw & 0xF0`(位置)/`(ppRaw & 0x0F)*16`(レーン拡張)/`token[2]`(レーン数字)という
  分解は数学的に等価であることを確認した。
- **フリーズ終点(E欄)は「形式はCと同じ」と明記。** これにより「終点の`'R'`が12分グリッドか
  24分グリッドか」の未確定事項が解消し、位置・始点・終点で完全に同一のfine文字ロジックへ
  統一した。
- **`'W'`という新規fine文字が判明。** 公式文書では`W`=`[24]-`(24分グリッドの減算、
  `S`=`[24]+`の符号反転)と説明されている。
- **`D`(フリーズの長さ)は「10進数値」と明記。** 後半の検証で、この一文が実は
  最も重要な手がかりだったと判明した(下記バグ1参照)。

## 2026-07-31(後半): test23key_v2.txt/test23key_v2_dos.txtとの突き合わせで判明した3件のバグ

23keyサンプルの初版(`test23key.txt`)をエクスポートした際、FUJIエディタ自身が「ノート間で
追い越しが発生しています 矢印番=3 小節=9 付近を確認してください」というエラーを出した。
これは測定9小節目の`aright`レーンに、S/Wを1マスごとに交互配置する密なテストパターンを
組んだことが原因で、S(pp%32==0で+32/3)とW(pp%32==16で−16/3)の定義上、隣接する2音が
数値上完全に同一のフレームへ丸められてしまうことによるもの(実装のバグではなく検証サンプルの
設計上の副作用)。ユーザーがこのレーンの密度を調整した`test23key_v2.txt`を再作成し、
エラー無しで最後まで正しくエクスポートされた`test23key_v2_dos.txt`を得たことで、
measure0〜10の全データが実測値として得られ、以下の3件の実装バグを発見・修正できた。

### バグ1: フリーズ終点のtail(`QQQQ`)は常に「先頭3桁=10進数値+末尾1文字=fine文字」であり、hexとして解釈してはいけない

旧実装は「`QQQQ`全4文字が16進として解釈できればそのままhexのdurとして使い、0x100以上は
−0x60補正する」という独自ルールを使っていた。これは公式文書の「Dは10進数値」という明記と
矛盾しており、実際に誤りだった。この補正式は先頭3桁が"01Y"型の値でしかたまたま成立せず
(例: 先頭3桁"012"は16進18・10進12で差が6、−0x60=−96の補正がちょうど16倍の差を
打ち消す)、それ以外の値では大きくずれる。test23key_v2.txtの`4860-0031`〜`48E0-0039`・
`C860-003A`〜`C8E0-003I`等、末尾が0〜9やA〜Fの数字系fine文字を意図したトークン群を
旧ルールで処理すると、実測値(frzDown等の各配列)と食い違うことを確認した。

正しくは**常に**「末尾1文字をfine文字とし、残り3文字を10進数値dとして読む」という単一
ルールであり、16進として解釈するケースは一切存在しない。

### バグ2: フリーズ終点のfine文字tail(`d`)は「始点からの長さ」であり絶対位置ではない

`sright`レーンの`4920-003R`(measure8, 始点pp=64)に対する実測値は`sfrzRight_data`の
`714,725`ペア。旧実装は終点の`d=3`を**絶対位置**として`pp=48`をそのままRのグリッド式に
適用しており、始点pp(64)より小さいため**終点が始点より前に来る不正な結果**になっていた。
正しくは**終点pp = 始点pp + d×16**(始点からの長さとして加算)であり、この式で計算すると
実測値と厳密一致した。これまでの検証サンプルは偶然すべて始点pp=0のケースしかなく、
このバグが発覚していなかった。

### バグ3: T/Xは「32刻みなら+8、それ以外は+0」ではなく、常に無条件で+8/−8

`oni`レーンの通常ノート(measure6/7、pos=0,64,128,192で全てT/X、いずれも整列位置)の実測値と
突き合わせて「pp自体に+8(=256/32)する式」がT/Xの正しい式だと判明した時点では、この4点が
すべて整列位置(pp%32==0)だったため、S/Wと同様「整列時のみ+8、非整列時は+0」という
アライメント依存式を暫定的に採用していた。しかし上記バグ1・バグ2の修正**前**の計算で
`sright`レーンの非整列位置(pp=240,%32==16)のフリーズ終点`C920-003T`を検証した際、
たまたま「非整列時+0」と実測値が一致したためこれを裏付けと誤認していた。バグ1・バグ2を
正しく修正した上で改めて`test23key_v2_dos.txt`(エラー無しの完全な実測データ)と突き合わせた
ところ、非整列位置でも**常に+8/−8**(アライメント非依存)が正しいと判明した
(`sright`の`0920-003X`など、非整列位置でのフリーズ終点実測値と厳密一致)。

## トークン構造(前提の再整理)

- 通常ノート(ダッシュ無し、常に4文字): `PPDF`
  - `PP`(2文字16進): 位置。上位ニブル=1/16刻みの粗い位置(0〜255スケール)、下位ニブルは
    23キー等でのレーン拡張ビット(`laneExt=(下位ニブル)*16`、2026-07-18c確定・変更なし)
  - `D`(1文字): レーン数字(そのままレーン番号、シフトなし)
  - `F`(1文字): fine文字(位置微調整、下記参照)
- フリーズ/speed/boost(ダッシュ区切り): `HHHH-DDDE`
  - フリーズ(`head[1]`が`'8'`または`'9'`。`'9'`はレーン+16拡張、変更なし):
    `head = P(1文字,1/16スロット) + M(1,'8'/'9') + D(1,レーン数字) + F(1,始点のfine文字)`
  - `DDDE`(終点): **常に**先頭3文字を10進数値`d`として読み、末尾1文字を始点と同じfine文字
    体系のfine文字として扱う(2026-07-31訂正: 16進として解釈するケースは無い)。
    **終点pp = 始点pp + d×16**(2026-07-31訂正: 絶対位置ではなく始点からの長さ)。
    終点はこの体系で始点と同じfine文字ロジックを適用して求める(始点側のfine補正の影響は
    受けない、実測で確認済み)。

## fine文字の規則(2026-07-31時点、全数実測検証済み)

| fine文字 | 意味 | 備考 |
|---|---|---|
| `0` | 補正なし(リテラル位置) | |
| `1`〜`9` | フレーム位置に+1〜+9フレーム | 旧実装は全レンジで`9−d`式を適用していたが、A〜Fの範囲でしか正しくなかった(修正済み) |
| `A`〜`I` | フレーム位置に−1〜−9フレーム(A=10,…,I=18として `−(値−9)`) | `G`/`H`/`I`は標準16進として無効なため、旧実装では警告スキップになっていた新規対応範囲 |
| `R` | 12分グリッドへの最近傍丸め(タイは後ろ優先): `n=floor(pp×3/64+0.5); finePp=n×64/3` | 位置・始点・終点のいずれでも同じ式。test23key_v2.txtの実測値と厳密一致 |
| `S` | 24分グリッドへの加算式: `finePp = pp + (pp%32==0 ? 32/3 : 16/3)` | 位置・始点・終点のいずれでも一致確認済み |
| `W` | 24分グリッドへの減算式: `finePp = pp - (pp%32==0 ? 32/3 : 16/3)` | 公式文書で新規判明。`S`の符号反転として実装(単独での実測点は少ないが密な配置での間接検証は一致) |
| `T` | pp自体に**常に**+8(=256/32)する式 | **2026-07-31最終確定**。整列・非整列いずれの位置でも実測値と厳密一致。アライメント依存(32刻みで係数が変わる)ではない、S/Wとは異なる単純な固定pp加算式 |
| `X` | pp自体に**常に**−8する式 | `T`の符号反転。同じく整列・非整列いずれでも実測値と厳密一致 |

なお通常ノートの`'R'`は、対象レーンでフリーズが小節境界を跨いでいる場合に限り
「フリーズ継続マーカー」として無視される(2026-07-15確定の既存仕様、フリーズ終点側の
`'R'`とは別物・変更なし)。

## 未確定事項(2026-07-31時点)

1. **`W`の単独実データ検証。** `S`の符号反転という推定で実装しており、test23key_v2.txtでも
   密な配置(S/Wの交互配置)での間接的な整合性は確認できたが、`W`単体を孤立した位置で
   検証した直接の実測例はまだ無い。
2. **レーン拡張マーカー`'9'`とフリーズ終点fine文字の広い組み合わせ。** `sright`

   fine文字(G/H/I等)の組み合わせ全般は未検証。

  - `IsKnownFineChar` — `W`/`T`/`X`を既知文字として明示

    使う」という旧ロジックを完全に削除し、常に`durPp = startPp + durDigit(10進) * 16.0`

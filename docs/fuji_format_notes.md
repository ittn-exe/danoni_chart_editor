# FUJIエディタ形式 調査メモ(2026-07-25)

`1224frztest.txt`(FUJIエディタネイティブ形式)と `1224frztest_dos.txt`(同ファイルをdanoniplus
dos.txtへエクスポートしたもの)をユーザーから提供頂き、全数比較でフリーズ関連の未確定事項を
解消した。本メモはその調査結果と、まだ確定しきれていない事項の記録。実装は
`src/DanoniEditor.Core/Import/FujiImporter.cs` に反映済み(該当箇所のXML docコメントにも
要約を記載)。

検証に使ったサンプルの前提条件: `$frame=0/2000/402000/1,400`(単一BPM区間、
mlen=100フレーム/小節、BPM=144、StartNumber(tick0フレーム)=200)。全5レーンが同じ
フリーズを同時に踏む譜面のため、`frzLeft_data`等5系統の出力はすべて同一の数値列になる。

## トークン構造(前提の再整理)

- 通常ノート(ダッシュ無し、常に4文字): `PPDF`
  - `PP`(2文字16進): 位置。上位ニブル=1/16刻みの粗い位置(0〜255スケール)、下位ニブルは
    23キー等でのレーン拡張ビット(`laneExt=(下位ニブル)*16`、2026-07-18c確定・変更なし)
  - `D`(1文字): レーン数字(そのままレーン番号、シフトなし)
  - `F`(1文字): fine文字(位置微調整、下記参照)
- フリーズ/speed/boost(ダッシュ区切り): `HHHH-QQQQ`
  - フリーズ(`head[1]`が`'8'`または`'9'`。`'9'`はレーン+16拡張、変更なし):
    `head = P(1文字,1/16スロット) + M(1,'8'/'9') + D(1,レーン数字) + F(1,始点のfine文字)`
  - `QQQQ`(終点): 全4文字が16進として解釈できればそのまま `dur`(0x100以上は−0x60補正、
    仕様15.3で検証済み・変更なし)として使う。**最後の1文字が16進以外(fine文字)の場合**、
    残り3文字を10進数値`d`とみなし `pp = d×16` とした上で、始点と同じfine文字体系で
    終点を求める。この終点計算は**トークン自身の開始小節・Pスロット基準**であり、
    始点側のfine補正の影響を受けない(実測で確認済み)。

## fine文字の規則(2026-07-25、21件のフリーズペア+60件のノート位置で全数検証・誤差ゼロ)

| fine文字 | 意味 | 備考 |
|---|---|---|
| `0` | 補正なし(リテラル位置) | |
| `1`〜`9` | フレーム位置に+1〜+9フレーム | **旧実装の誤りを修正**。旧実装は全レンジで`9−d`式を適用していたが、これはA〜Fの範囲でしか数学的に正しくなかった。旧実装のコメントには「1〜8は実例未観測の外挿」と明記されており、今回のサンプルでその外挿が誤りだったと判明(正しくは+1〜+9、旧式は+8〜+1を返していた) |
| `A`〜`I` | フレーム位置に−1〜−9フレーム(A=10,…,I=18として `−(値−9)`) | `G`/`H`/`I`は標準16進(`NumberStyles.HexNumber`)として無効なため、旧実装では警告スキップになっていた新規対応範囲 |
| `T` | 常に+3フレーム(固定値) | 旧実装は「pp+8単位」説(比例的な32分音符相当の解釈)だったが、今回は固定+3フレームの方が単純に一致。ただしサンプルのmlenが100という特殊値のため、`8/256×100=3.125≈3`と偶然一致してしまい、両説を数値上区別できていない。異なるmlen値のサンプルでの追加検証が望ましい |
| `X` | 常に−3フレーム(固定値) | 新規判明。Tの逆 |
| `R` | ノート位置・フリーズ始点では12分グリッドへの最近傍丸め(タイは後ろ優先): `n=floor(pp×3/64+0.5); finePp=n×64/3`(旧実装のR式のまま、変更なし) | フリーズ**終点**でのRは下記「未確定事項」参照 |
| `S` | 24分グリッドへの加算式: `finePp = pp + (pp%32==0 ? 32/3 : 16/3)`(旧実装のS式のまま、変更なし) | ノート位置・フリーズ始点・フリーズ終点のいずれでも一致を確認済み |

なお通常ノートの`'R'`は、対象レーンでフリーズが小節境界を跨いでいる場合に限り
「フリーズ継続マーカー」として無視される(2026-07-15確定の既存仕様、フリーズ終点側の
`'R'`とは別物・変更なし)。

## 未確定事項(2026-07-25時点)

1. **フリーズ終点の`'R'`が本当に24分グリッド式(S式)を使うのか、12分グリッド式(R式本来の式)を
   維持しているのかが未確定。** サンプル中のフリーズ終点`'R'`は実例が2件(d=1, d=2)しかなく、
   いずれも12分グリッド式と24分グリッド式が数値上たまたま一致する位置だったため区別できていない。
   現在の実装は暫定的にS式(24分グリッド)を両方に適用している
   (`FujiImporter.cs`内`DurationQuantizedPp`参照)。
2. **フリーズ終点側で数字系(`1`〜`9`, `A`〜`I`)のfine文字を使うケースは実例が無く未検証。**
   現在の実装は始点と同じ`LiteralFrameShift`をそのまま適用しているが、これは類推であり
   実データでの裏取りはできていない。
3. **`T`/`X`が「固定+3/−3フレーム」なのか「pp+8単位(比例)」なのかが完全には区別できていない。**
   サンプルのmlenが100という値のため、両説が数値上ほぼ一致してしまう(上表参照)。異なるmlenの
   サンプルがあれば一意に確定できる。
4. **レーン拡張マーカー`'9'`とフリーズ終点fine文字の組み合わせは未検証。** サンプル中のフリーズは
   すべて`'8'`(非拡張)フラグのみで、`'9'`(レーン+16拡張)を伴うフリーズの終点fine文字の実例が無い。

  - `DurationQuantizedPp` — フリーズ終点(duration)専用のR/S式(現状は両方ともS式、未確定事項1参照)
